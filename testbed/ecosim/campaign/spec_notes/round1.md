## D1 — Activation Code (C2a) · §4.1 (pp.211-213), reject behavior §3.1.3.1 steps 1-2

Grammar (Table 8, `$`-delimited plain ASCII, NOT ASN.1 on this leg):
`[LPA:]AC_Format $ SM-DP+Address $ AC_Token(matchingId) [$ SM-DP+OID [$ CCRequiredFlag [$ CIPKIndicator [$ DeleteNotifForDeviceChange]]]]`
- `AC_Format` MUST be literal `"1"`; any other value → LPA SHALL treat AC as invalid.
- SM-DP+ Address: FQDN, QR-alphanumeric charset (ISO/IEC 18004 tbl5) excluding `$`.
- AC_Token (matchingId): charset `[0-9A-Z-]` only; MAY be zero-length.
- CCRequiredFlag: literal `"1"` if present (no `"0"` defined).
- CI Public Key indicator: even-length hex, optional `-`.
- Max length 255 chars (unless carrying Delete Notification for Device Change).
- QR delivery SHALL prefix `LPA:`.
PROTECTION: none — bare plaintext, no sig/MAC. TOFU; trust established later when SM-DP+ proves CERT.DPauth.SIG chains to CI (§3.0.1).
CONFORMANT LPA SHALL: reject invalid format; reject AC_Format!="1"; if CIPKIndicator present verify against eUICCInfo1 supported list or abort; at mutual-auth step 10 verify SM-DP+ OID in cert == AC OID (if present) else CancelSession+stop; ignore unknown trailing params (forward-compat).
MUTABLE-IN-REALITY: YES if digitally delivered (web QR/deeplink/SMS) — free substitution of address/matchingId. Impact bounded: redirect needs attacker to ALSO hold CI-signed CERT.DPauth.SIG → gives redirection/DoS/CC-bypass, NOT profile forgery.

## D2 — ES10b AuthenticateServer input (C3) · §5.7.13 (pp.334-338), §5.6.1 Table36 Note6, §3.0.1

ASN.1 (tag BF38):
```
AuthenticateServerRequest ::= [56] SEQUENCE {
  serverSigned1 ServerSigned1,                  -- the ONLY signature-covered part
  serverSignature1 [APPLICATION 55] OCTET STRING (5F37),
  euiccCiPKIdToBeUsed SubjectKeyIdentifier OPTIONAL,  -- NOT signed
  serverCertificate Certificate,                -- self-verifying via PKI
  ctxParams1 CtxParams1,                         -- built by LPAd, UNSIGNED at this hop
  otherCertsInChain [1] OPTIONAL, crlList [2] OPTIONAL }
ServerSigned1 ::= SEQUENCE { transactionId[0], euiccChallenge[1] Octet16, serverAddress[3] UTF8String,
  serverChallenge[4] Octet16, sessionContext[5] OPTIONAL, serverRspCapability[6] OPTIONAL }
CtxParams1 (CHOICE) CtxParamsForCommonAuthentication: matchingId, deviceInfo, operationType, iccid(RPM), matchingIdSource
```
PROTECTION: only serverSigned1 covered by serverSignature1. euiccCiPKIdToBeUsed NOT signed — SM-DP+ enforces integrity RETROACTIVELY (Note 6: verifies eUICC cert chains to root identified by this value at AuthenticateClient). ctxParams1 unsigned at LPA→eUICC hop.
**KEY:** eUICC "SHALL neither check the values provided in ctxParams1 (other than the ICCID in ctxParamsForDeviceChange) nor correlate them with subsequent session activities." → eUICC will SIGN attacker-chosen matchingId/deviceInfo/operationType into EuiccSigned1. Backstop is the SM-DP+ (§3.1.3 step3: verify pending order for provided MatchingID).
eUICC SHALL verify (error→terminate): session exists (noSession); server cert chain via PK.CI.SIG (ciPKUnknown/invalidCertificate); cert type CERT.DPauth/DSauth.SIG (invalidOid); serverSignature1 over serverSigned1 (invalidSignature); euiccChallenge matches session (euiccChallengeMismatch); CI PKID supported+creds present, empty/omitted fails (ciPKUnknown); CRL checks if stapled; ICCID installed if deviceChange (invalidIccid).
MUTABLE-IN-REALITY: on-device LPA↔eUICC (APDU) hop — YES, ctxParams1 + euiccCiPKIdToBeUsed fully mutable (THIS PROJECT'S TARGET boundary). WAN hop is TLS-pinned. euiccCiPKIdToBeUsed tamper → limited (SM-DP+ catches). matchingId tamper → eUICC signs attacker context; SM-DP+ order-check is real backstop.

## D3 — ProfileMetadata / StoreMetadataRequest · §4.4 (pp.227-228), §5.5.3 (BF25), §5.6.3 Table41

ASN.1 StoreMetadataRequest ::= [37] SEQUENCE (BF25): iccid, serviceProviderName[17] UTF8(0..32) M, profileName[18] UTF8(0..64) M,
  iconType[19] O, icon[20] OCTET(0..1024) O, profileClass[21] DEFAULT operational, notificationConfigurationInfo[22] O,
  profileOwner[23] O, profilePolicyRules[25] O, ... Only iccid/SPN/profileName mandatory.
**TWO COPIES, DIFFERENT PROTECTION:**
1. Consent-time copy = `profileMetadata` output field of ES9+.AuthenticateClient (§5.6.3 Table41). §4.4: "generated by the SM-DP+ **in plain text** to be readable by the LPA." NOT covered by smdpSignature2 — SmdpSigned2 = {transactionId, ccRequiredFlag, bppEuiccOtpk, rpmPending} only, NO metadata hash. Only TLS transport protects it.
2. Install-time copy = StoreMetadata inside BPP (§5.5.3), BSP-protected end-to-end (S-ENC/S-MAC or PPK). LPA is blind relay, cannot tamper undetected.
**NO spec mechanism requires the LPA to reconcile the two copies.** §3.1.3.1 only informally notes "same metadata will also be available" — UX, not security binding.
eUICC install-time SHALL check: profileClass supported (unsupportedProfileClass); ICCID not already installed; PPR/profileOwner consistency; enterprise checks; unknown TLV → unknownTlvInMetadata. None re-verify against consent copy.
MUTABLE-IN-REALITY: consent copy is TLS-protected on WAN but NOT app-layer authenticated → a malicious/compromised LPA (or code between TLS termination and the consent UI) can show benign profileName/SPN/icon while a DIFFERENT metadata is bound in the BPP. Genuine "shown ≠ installed" REAL-GAP.

## Testbed fidelity implications (lead to reconcile)
- Our SmdpSigned2 currently = concat_len(transactionId, iccid) — spec says iccid is NOT in SmdpSigned2. profileMetadata already a separate un-signed field (correct). Fix signed content to {transactionId, ccRequiredFlag, bppEuiccOtpk} for fidelity; keeps metadata un-bound (the gap).
- ctxParams1/matchingId not yet carried into our AuthenticateServer→EuiccSigned1. Add it so D2 can be modeled (eUICC signs unchecked ctxParams1).
- Consent metadata is invariant across honest runs, so the variable-only fuzzer skips it. D3 must fuzz it explicitly (attacker-mutable field, integrity gap) even though invariant.
